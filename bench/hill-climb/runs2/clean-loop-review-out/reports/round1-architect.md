A negative `window` makes `cutoff > now`, which also drops every stamp and always allows. `limit=float('inf')` always allows. In each case the limiter fails open, not closed. | Anyone who builds a limiter directly instead of through `load_config` can quietly end up with no limiting at all. | Add one private validator module (e.g. `ratelimit/_validate.py` with `positive_finite(name, v)` and `positive_int(name, v)`, raising `ConfigError`). A-2 | high | ratelimit/config.py:35-46 | The checks are `float(...)` / `int(...)` followed by `<= 0`. In Python every comparison with nan is False, so `nan <= 0` is False and NaN passes; `inf` and the strings `"nan"`, `"inf"`, `"1e999"` pass too. `bool` passes because `int(True) == 1` and `float(True) == 1.0`. `int(2.7)` silently truncates `burst` to 2, and `int(0.5)` becomes 0, which is then rejected with the misleading message "burst must be positive". The frozen `test_values` (tests/test_config.py:10-12) requires numeric strings to be accepted, so the type rules have to be written down explicitly rather than inherited from whatever `float()` happens to accept. | Bad config such as `{"rate": NaN}` or `{"burst": true}` is accepted and produces a limiter that misbehaves, which breaks DoD item 3. | In the shared validator from A-1: reject `bool` before converting; accept `int`, `float` and numeric `str`; require `math.isfinite(v) and v > 0`; for `burst`, require a whole value (`float(v).is_integer()`) and do not truncate. `None` already raises `TypeError`, which is mapped to `ConfigError`; keep that. | Add parametrized tests that each of these raises `ConfigError`: `{"rate": float('nan')}`, `{"rate": "inf"}`, `{"window": float('inf')}`, `{"burst": True}`, `{"rate": False}`, `{"burst": 2.7}`, `{"burst": None}`, `{"rate": -0.0}`. Re-run `test_values` to confirm string coercion still passes. | high

A-3 | medium | ratelimit/limiter.py:37, 42 | A denied call still writes the rounded token count back (`self._buckets[key] = (tokens, now)`). With fractional rates, the error from each `+= elapsed*rate` step therefore accumulates across every denied poll. Worked from float semantics: with `rate=0.1, burst=1`, take the first token, then poll once per second. Tokens go 0.1, 0.2, 0.30000000000000004, …, and after 10 s the total is 0.9999999999999999 < 1.0. The request is denied at t=10 and only allowed at t=11. `rate=0.5` happens to be exact in binary, so a test that uses only 0.5 would pass while the general fractional case is wrong. | Clients that poll at sub-1/s rates are throttled more than configured, and how much depends on how often they poll. | Smallest fix: on a deny, do not write the bucket back. Leaving `(tokens, last)` unchanged means the next call computes `tokens + (now - last)*rate` in a single multiplication, so error does not build up. (A GCRA "theoretical arrival time" design also avoids it but is a bigger change.) Optionally compare against `1.0 - 1e-9`. | Add a test with `RateLimiter(0.1, 1, FakeClock)`: allow once, then `advance(1.0)` and call `allow` ten times; the tenth call must return True. Also add the DoD test for 0.5: True at t=0, False at t=1, True at t=2. | high

A-4 | medium | ratelimit/limiter.py:34-39, 70-77 | The `try/except` stops exceptions escaping, but it does not stop bad clock values from being stored. I worked this from Python semantics and did not run it. If `clock()` returns nan once, `min(float(burst), nan)` returns `float(burst)` (because `nan < x` is False), so the bucket is stored as `(burst-1, nan)`. Every later `elapsed` is then nan, `min` again returns `burst`, and that key is allowed on every call from then on. In `SlidingWindow`, a nan `now` drops all stamps and logs `[nan]`, which also fails open. A clock that goes backwards gives a negative `elapsed`, which drains tokens. That denies (fails closed) but is still corrupted state. | A single bad clock reading can turn a key into "always allow" with no exception raised. DoD item 3 ("no state is corrupted") is not met. | Check inputs before committing anything: in both `allow` methods, after reading `now`, `if not math.isfinite(now): return False` (counted as denied), and clamp `elapsed = max(0.0, now - last)`. Write state only after every computed value has passed. With this, the existing `except` stays as a second safety net and is not the only defence. | Add tests with a clock that returns `[0.0, nan, 1.0, 2.0, …]`: every call from the nan one onward must return False until tokens genuinely refill, and `_buckets[key][1]` must never be nan. Run the same sequence against `SlidingWindow`. Add a separate test where the clock raises: `allow` returns False and `_buckets`/`_log` are unchanged. | med

Only `RateLimiter` has `stats`; `SlidingWindow` has none, so the two limiters behave differently for metrics. | Operators cannot see fail-closed denials. ### Out of scope (optional, one line each)
- `_buckets` and `_log` are never evicted, so memory grows without limit when keys come from untrusted input such as client IPs.
- `Config` has no `limit` field, so a `SlidingWindow` cannot be built from a loaded config without reusing `burst` as the limit.
- `isinstance(raw, dict)` at config.py:30 rejects non-dict `Mapping` types (for example `MappingProxyType`).
- `SlidingWindow.allow` reads `clock()` outside the lock (limiter.py:70). The count is still correct, but stamps can be added out of order; moving the read inside the lock would match `RateLimiter`.
